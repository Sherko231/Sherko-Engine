# Sherko Engine Decision Log

This is the durable, append-only summary of accepted engineering decisions. It records why the repository is shaped this way without mixing in live task status. New entries receive the next ID; superseded entries remain and link to the replacement.

## Status values

- `Accepted` — binding unless deliberately superseded.
- `Provisional` — usable for current work but requires a named validation gate.
- `Superseded` — historical; a later decision controls.

## Decisions

| ID | Status | Decision | Rationale / consequence |
| --- | --- | --- | --- |
| D-001 | Accepted | Authored engine and game runtime source is Java 25 only; Gradle Kotlin DSL is allowed for build configuration. | Preserves the Java-only product constraint without a no-value build-script migration. |
| D-002 | Accepted | Windows x64 and Steam are the initial release platform/social layer. | Keeps native verification and packaging bounded for v1. |
| D-003 | Accepted | OpenGL 4.6 Core with a forward renderer is the first renderer. | Smaller v1 implementation surface than Vulkan; multiple backends remain deferred. |
| D-004 | Accepted | Jolt through Jolt JNI supplies rigid-body physics; native objects use explicit ownership/cleanup. | Avoids building a solver and prevents treating GC as native-resource management. |
| D-005 | Accepted | Multiplayer uses server-authoritative simulation, not deterministic physics lockstep. | Physics-heavy shared objects are corrected/replicated from the server; clients do not own arbitrary authoritative transforms. |
| D-006 | Accepted | Production networking uses transport-neutral APIs with direct-IP and Steam adapters; no home-grown reliable UDP transport. | Keeps gameplay independent of transport and limits custom protocol risk. |
| D-007 | Provisional | Java FFM may call the Steam flat API without authored C/C++ glue. | API/pointer access is proven; P0-T09A / Issue #42 must prove end-to-end connection, callbacks, message release, and cleanup before production use. |
| D-008 | Accepted | Runtime game UI is an engine-owned retained, renderer-neutral model; imgui-java is editor/debug only. | Prevents shipped UI/game state from coupling to OpenGL or internal tooling and includes keyboard/controller navigation. |
| D-009 | Accepted | glTF 2.0 is authoring interchange; gameplay loads cooked engine formats. | Separates flexible import from bounded/versioned runtime data. |
| D-010 | Accepted | Disk/network formats use explicit versioned codecs; Java object serialization is forbidden. | Provides bounded compatibility and avoids unsafe, implicit layouts. |
| D-011 | Accepted | v1 gameplay is first-person; third-person presentation follows a stable multiplayer vertical slice. | Core player/authority contracts stay camera-agnostic without blocking the first playable loop. |
| D-012 | Accepted | Target is 1–4 supported players, with intended co-op sessions of 2–4, in small/medium complete-scene levels. | Bounds replication, hosting, content, and performance work; open-world streaming is deferred. |
| D-013 | Accepted | Agent-authored changes use one Issue, one dedicated branch, one pull request, and CI before merge. | Makes handoff state reviewable and prevents undocumented direct changes to `master`. |
| D-014 | Accepted | Commit-contained status and live workflow status are separate. | `docs/DEVELOPMENT_STATUS.md` describes its containing commit; GitHub Issues/Project describes activity after that commit. |
| D-015 | Accepted | The 15-second P0-T12 combined run is a smoke test, not a soak test. | P0-T13 / Issue #43 owns the 15-minute sustained run; P0-T14 / Issue #44 owns repeated lifecycle evidence. |
| D-016 | Accepted | Every declared Gradle subproject owns an explicit package root and exposes only its declared `.api` root as a cross-module contract; declared `.internal` roots are implementation details and must not be imported by other modules. | Makes module boundaries machine-checkable without designing future subsystem APIs early. A source-scanning architecture test validates the registry and rejects cross-module implementation imports, including a representative game-to-platform shortcut. |
| D-017 | Accepted | D-016 verification derives its complete subproject inventory from Gradle and parses main/test Java source with the JDK compiler-tree API; production sources must declare an owned package, while test-package ownership is intentionally excluded. | Prevents hard-coded module drift, missing-package bypasses, fully qualified implementation shortcuts, and overlapping-root misattribution without adding a parser dependency. This is source-level enforcement and does not claim bytecode, reflection-string, resource, or out-of-tree generated-source coverage. |
| D-018 | Accepted | P2-T01 / Issue #64 defines `EngineSubsystem` as an abstract `AutoCloseable` base with final guarded lifecycle methods and protected phase hooks. One instance is initialized, started, stopped, and closed once; unstarted or failed instances can be explicitly closed. Forward hook failures propagate unchanged and allow only cleanup; close is attempted at most once even on failure. Calls are externally serialized and reentrant transitions are rejected. | Makes single-subsystem ordering executable without prematurely implementing a dependency graph or coordinated rollback. Cleanup hooks tolerate partial setup and failed activation/stopping. A failed cleanup is not proof of resource release. This does not authorize native restartability claims or supersede P0-T14. |
| D-019 | Accepted | P2-T02 / Issue #72 adds an immutable, non-owning `SubsystemGraph` registration snapshot with deterministic depth-first dependency ordering. Construction rejects duplicate IDs/instances and missing prerequisites; resolution rejects cycles with a closed diagnostic path and returns only a complete unmodifiable order. Graph operations invoke no lifecycle methods. | A manual list cannot validate declared dependencies; graph-only resolution supplies that validation without a lifecycle manager, service locator, new dependency, or rollback. The caller resolves before initialization and retains D-018 ownership/cleanup duties. Iterative traversal avoids call-stack limits. P2-T03 retains coordinated rollback; native and phase-exit evidence is unchanged. |
| D-020 | Accepted | P2-T03 / Issue #73 adds stateless `SubsystemStartup.start(List<EngineSubsystem>)` coordination for an already resolved dependency-first order. Startup activates each subsystem with `initialize()` then `start()` before advancing. On initialize/start failure, it preserves the original throwable, closes the failing subsystem, then stops and closes previously started subsystems in reverse order; rollback failures are suppressed on the original failure. Successful startup retains caller ownership and normal shutdown responsibility. | P2-T02 produces validated ordering but intentionally performs no lifecycle work. Centralizing only partial-startup rollback prevents duplicated try/finally logic without introducing a general lifecycle manager, state accessor, restart contract, dependency injection framework, or normal-shutdown owner. The utility is synthetic Java lifecycle evidence only and does not establish native restartability, leak freedom, sustained stability, or the P2 phase exit. |
| D-021 | Accepted | P2-T04 / Issue #74 adds `EngineClock` as a small elapsed-nanosecond sampler. The default source is `System.nanoTime`; tests may inject a `LongSupplier`. Construction does not sample. The first successful sample returns zero, later samples return `current - previousAccepted`, zero elapsed is valid, and a negative signed difference is rejected without advancing the accepted baseline. Raw source values may be negative; ordinary `long` subtraction intentionally preserves forward intervals below `2^63` ns across signed wraparound. Source failures propagate unchanged and do not advance state. Calls are externally serialized. | Centralizes deterministic monotonic elapsed sampling without assigning fixed-step, pacing, catch-up, interpolation, wall-clock, frame-identity, or concurrency policy to the clock. Integer nanoseconds avoid premature floating-point rounding policy and provide the direct input needed by P2-T05 while keeping later timing tasks separately testable. |
| D-022 | Accepted | P2-T05 / Issue #75 adds `FixedStepAccumulator` as a stateful integer/rational conversion from non-negative elapsed nanoseconds to newly due whole simulation ticks at exactly 60 ticks per 1,000,000,000 ns. Fractional progress is retained exactly across calls; negative input is rejected without mutation; zero is valid; all non-negative `long` inputs, including `Long.MAX_VALUE`, are supported without intermediate overflow. The caller owns tick execution/counting and externally serializes calls. | Preserves cadence-independent fixed-step progress without rounding 1/60 second to an integer nanosecond duration or introducing floating-point drift. The accumulator deliberately excludes frame-gap clamping, catch-up limits, interpolation exposure, pacing, callbacks, lifecycle integration, and configurable tick rates, which remain later bounded tasks. |

## Adding or changing a decision

An Issue must explicitly authorize a durable architecture change. Add a new row with its evidence/gate, update `docs/ARCHITECTURE.md` where structure changes, and reconcile `ENGINE_SCOPE.md` when the product boundary changes. Never rewrite an old decision to hide history; mark it `Superseded` and add the replacement.
